## 1. 背景与问题

病房健康教育长期依赖口头讲解、纸质单和公众号图文。讲解难复现、家属不在场就中断、护理部难以证明「该讲的讲了」。材料把目标概括为宣教工作的标准化、流程化、数据化、智能化，并要求「有平台、有内容、有场景、有成果」。

对标产品 HEALS 已验证「扫码入科 → 标记组 → 群发/计划推送 → 已读留痕」在多家医院可运转，但操作手册显示它是**科室健康教育中心**：医护角色不分、智能推送靠标记组加时间、没有责任护士待办、没有入院包/出院包作为一等公民、没有当面补讲闭环。护理部考核要的是覆盖率、路径是否在 24 小时内完成、满意度与知晓率，而不是再做一个内容站。

宣武 POC 需要先在**不接 HIS、不接医院服务号**的前提下，用 SaaS 把护理作业跑通，再把患者触达做到微信小程序。

## 2. 目标用户与场景

本期只做**住院病房**。门诊、日间、检查、手术室名单（02.2）延期。

| 用户 | 场景 | 失败时的代价 |
| --- | --- | --- |
| 责任护士 | 入科当天完成入院宣教包，知道谁没看 | 漏讲、纠纷时说不清 |
| 护士长 | 分床、启用路径、控制全科群发 | 误推、口径不统一 |
| 护理部 | 看各科覆盖、未读、24h 完成、月报 | 健康促进/质控无法举证 |
| 患者与家属 | 床头或床旁屏反复学习出院与用药 | 只听一次记不住 |
| 信息科 | 问数据是否出域、谁推了什么 | 不合规即无法上线测试 |

不服务：互联网医院运营、患友社群运营、直播间、医患即时咨询值班。

## 3. 产品定位

**护理推送平台是护士可完成、护理部可考核的宣教作业台。**

它不是：

- HEALS 式全量健康教育中台（直播、患友会、咨询、培训课件库）
- HIS 护理文书或电子签名系统
- 短信群发工具或医院服务号替代品

价值落到材料的四句话：

| 主张 | 产品落点 |
| --- | --- |
| 有平台 | 护理部/护士长可控的 Web；责任护士默认只看自己的床 |
| 有内容 | 科室知识库 + 院内共享 + 公共库引用；入院到康复分类 |
| 有场景 | 病房床头码、同一链接的床旁屏、二期微信小程序 |
| 有成果 | 有效阅读、路径 24h 完成率、问卷知晓率、护理满意度、月报 |

## 4. 范围

基线为勾选表(2)：**纳入 59、延期 3、不做 38**。详细编号见用例分析第 3 节与 PRD 附录。

### 4.1 做（纳入）

- 组织与责任床、手建/导入患者（无 HIS）
- 路径包（入院/手术/出院/病种）、审核启用、一键套用
- 群发与智能计划（含未读次日补推、护士长确认全科群发）
- 阅读任务：待推 / 未读 / 当面补讲（护士点完成，不做签收交班）
- 问卷：随访/知晓率评分/护理满意度；分层考试复用问卷，无课件库
- 质控看板与月报
- 患者 H5 + 授权文案 + 入科必填表单 + 专病专区
- 床旁屏：出码/给链接，屏用浏览器打开
- 二期：患者小程序、订阅消息、医护微信邀请码

### 4.2 延期（V1.1，不进本期排期）

- 02.2 非病房名单
- 02.7 扫码人数上限
- 02.10 家属单独推送策略

### 4.3 不做

咨询、患友会、直播、讲堂、培训课件、HIS 事件、服务号模板、短信、电子签字、任务催办与交班、文章读完弹问卷、秀米、多医院切换、等保院内部署形态、AI 生成与问答。

延期与不做必须分开：延期是明确下一档；不做须改勾选并升版本才能进 backlog。

## 5. 分期

```mermaid
flowchart LR
  accTitle: 两期交付
  accDescr: 先 SaaS 与 H5 测闭环，再小程序触达

  P1[P1_医护Web与患者H5与床旁出码] --> Demo[护理部可演示作业闭环]
  Demo --> P2[P2_患者小程序与订阅消息]
```

| 期次 | 形态 | 目的 |
| --- | --- | --- |
| P1 | 医护 Web + 患者 H5/床头码 + 床旁屏链接 | 无微信审核也能测「推得出、看得完、有数据」 |
| P2 | 患者小程序 + 订阅消息；邀请码升级为微信码 | 降低患者打开成本；配置仍在 Web |

后端从 P1 起按多端复用：路径、群发、计划都写成同一 `PushTask`，小程序不得另建阅读表。

单院租户即可（01.6 不做）。组织树仍按医院 → 院区 → 科室 → 病区建模，避免写死单科室。

## 6. 与 HEALS 的差异（给评审用）

| 维度 | HEALS | 本产品 |
| --- | --- | --- |
| 用户模型 | 科室医护基本不分 | 责任护士 / 护士长 / 护理部 / 质控 |
| 主对象 | 宣教中心 + 标记组 | 宣教路径包 + 责任床任务 |
| 没看怎么办 | 已读统计 | 未读进当面补讲；计划可次日补推 |
| 管理成果 | 阅读率、人工月报 | 24h 路径完成率、满意度、知晓率、系统月报 |
| 明确不做 | 手册含咨询、患友会、直播、培训 | 勾选为不做（考试仅问卷成绩） |

可复用 HEALS 已验证的：扫码入科、床位、标记组、群发/定时、阅读时长、问卷。

## 7. 成功标准

P1 对护理部演示通过，即视为 POC 功能成功（非科研终点）：

1. 一条入院路径从审核到套用可走通。
2. 患者经授权和表单进入 H5，有效阅读可回写护士端。
3. 未读出现在当面补讲并可由护士关闭。
4. 全科群发可走护士长确认；满意度可导出。
5. 护理部能按科室看覆盖率、24h 完成率并下载月报。
6. 审计能查出谁对哪位患者推了哪篇。
7. 另一演示租户看不到本院数据。

约束：无 HIS、无短信；POC 须口头说明数据托管位置（16.5 不做院内部署，但信息科问题必须有答案）。

## 9. 风险

| 风险 | 应对 |
| --- | --- |
| 患者不扫码 | P1 用床旁屏同链；P2 订阅消息；不做短信 |
| 无 HIS 导致名单负担 | Excel 导入；手术日手填 |
| 内容空洞 | 试点科室先做入院/出院/1–2 个病种包，公共库引用 |
| 小程序审核周期 | P1 不依赖小程序即可验收 |
| 咨询值班压力 | 已整模块不做 |
| 勾选 15.2 无课件 | 考试=问卷，文档已写死 |

## 10. 术语

| 术语 | 含义 |
| --- | --- |
| Stay | 一次在院/在科经历，码和任务都挂在这里 |
| 路径 | 按锚点展开的宣教包 |
| PushTask | 对一名在院患者的一条执行对象 |
| 有效阅读 | 停留时长达到科室阈值 |
| 当面补讲 | 未读或须当面的条目，护士床旁完成后关闭 |
| 纳入 / 延期 / 不做 | 勾选表三态，见第 4 节 |
